1. Introducción

VitrinaSur es una aplicación web orientada a la exhibición de productos y productores locales de Chiloé. Permite explorar categorías, consultar productos, conocer productores y realizar prepedidos.

El proyecto utiliza una arquitectura Full Stack con frontend React, backend Express y base de datos PostgreSQL.

2. Arquitectura del sistema

VitrinaSur utiliza una arquitectura cliente-servidor organizada en tres capas.

  • Frontend: React y Vite, desplegados en Vercel.
  • Backend: Node.js y Express, desplegados en Render.
  • Persistencia: PostgreSQL, alojado en Neon.

El frontend consume endpoints HTTP de la API REST. El backend procesa solicitudes y consulta la base de datos.

3. Modelo de base de datos PostgreSQL

VitrinaSur utiliza PostgreSQL para almacenar usuarios, categorías, productores, productos y prepedidos. El esquema local contiene cinco tablas.

3.1 Tablas del sistema

Tabla Clave primaria Descripción
usuarios id Cuentas y roles de acceso.
categorias id Clasificación de productos.
productores id Información de productores locales.
productos id Catálogo de productos.
prepedidos id Solicitudes y valores de prepedidos.

3.2 Relaciones entre tablas

  • Categorías → Productos (1:N): productos.categoria_id referencia categorias.id.
  • Productores → Productos (1:N): productos.productor_id referencia productores.id.
  • Productos → Prepedidos (1:N): prepedidos.producto_id referencia productos.id.

La tabla usuarios almacena información de autenticación y roles. No se ha confirmado una clave foránea que la relacione directamente con las demás tablas.

3.3 Restricciones de integridad

  • Las cinco tablas utilizan claves primarias id.
  • El nombre de cada categoría debe ser único.
  • La cantidad de un prepedido debe estar entre 1 y 100.
  • El precio unitario y el total no pueden ser negativos.
  • El estado inicial de un prepedido es pendiente.
  • La fecha del prepedido utiliza CURRENT_TIMESTAMP por defecto.

3.4 Campos de productores

La tabla productores contiene: id, nombre, descripcion, ubicacion, imagen, comuna y categoria.

El identificador y el nombre son obligatorios. El identificador es la clave primaria.

3.5 Campos de categorías

La tabla categorias contiene: id, nombre y descripcion.

El nombre es obligatorio y posee una restricción de unicidad.

3.6 Campos de prepedidos

Campo Tipo Descripción
id integer Clave primaria.
producto_id integer Referencia al producto.
nombre varchar(150) Nombre del cliente.
telefono varchar(30) Teléfono de contacto.
cantidad integer Unidades solicitadas.
fecha timestamp Fecha de registro.
estado varchar(30) Estado del prepedido.
precio_unitario numeric(12,2) Precio por unidad.
total numeric(12,2) Importe total.

Nota: esta estructura corresponde a PostgreSQL local. Queda pendiente verificar su equivalencia con la base de producción en Neon.

4. Catálogo de API REST

URL base pública: https://vitrinasur-backend.onrender.com/api

Método Endpoint Descripción
GET /productos Consultar productos disponibles.
GET /categorias Consultar categorías.
GET /productores Consultar productores.

El catálogo se ampliará con las operaciones CRUD, autenticación, parámetros y códigos HTTP verificados.

5. Seguridad y autenticación

El sistema incorpora autenticación con JWT, gestión de sesiones mediante cookies y autorización basada en roles.

Las credenciales y secretos de configuración deben permanecer fuera del repositorio público mediante variables de entorno.

El backend dispone de middleware para verificar la autenticación y restringir determinadas operaciones administrativas.

6. Auditoría de IA generativa

Durante el desarrollo se utilizó ChatGPT como herramienta de asistencia para comprender errores, proponer cambios, revisar componentes y apoyar la documentación.

6.1 Ejemplos de asistencia

  • Corrección de errores de navegación con React Router.
  • Apoyo en la integración del frontend con la API.
  • Diagnóstico de problemas de conexión con PostgreSQL.
  • Revisión de autenticación y validaciones.
  • Correcciones de diseño responsivo y estilos CSS.

6.2 Verificación humana

Las soluciones propuestas se revisaron y probaron durante el desarrollo mediante pruebas de navegación, compilación, solicitudes HTTP y consultas a la base de datos.

Las evidencias específicas de los problemas, correcciones y resultados se incorporarán en la versión definitiva.
